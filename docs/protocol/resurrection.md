# 復活確認與移動鎖定（T151／#414）

## 已驗證的 wire 契約

依 [server-protocol.md](../reference/server-protocol.md)、[server-rules.md](../reference/server-rules.md) 與 [source-vs-jar.md](../reference/source-vs-jar.md)，唯讀核對本機來源，並用 `javap -c` 核對 d287 JAR 的 `C_Attr.start`、`S_Lock.buildPacket`、`C_UnLock.start`。未執行伺服器。下列為明文 payload；C／H／D 是 1／2／4 bytes，H／D little-endian，現有傳輸層補零至 8 的倍數。

| 方向 | 格式 | 意義 |
|---|---|---|
| S219 | `C219 H0 D0 H321`／`H322` | 「是否要復活？」確認，沒有字串。321 來自一般復活卷軸，322 來自祝福復活卷軸等 |
| C121 | `C121 H0 D0 H321／322 C(answer)` | answer=1 接受、0 拒絕；D 固定 0，不是 requestId，不走 622 路徑 |
| S85 | `C85 D(target) C(type) D(caster) D(gfx)` | 復活動作，目前只有 type 0。由 `Recovery.cs` 既有路徑解析 |
| S241 | `C241 C0` | 移動鎖定；**固定內容，沒有解除旗標或解除封包** |

範例（含補零）：S219/321 `DB000000000000410100000000000000`；C121 接受 321 `79000000000000410101000000000000`；拒絕 322 `79000000000000420100000000000000`；S241 `F100000000000000`。

d287 `C_Attr` 先讀 H；若為 0 再讀 D 與訊息 H，`lookupswitch` 含 321、322。兩個分支都讀 C，依 TempID 找施放者並清除 TempID。接受時原服先送特效並設定 HP，再廣播 S85 與 S119。**拒絕時原服不回包；施放者已離線時原服也不回包**，所以接受後等不到 S85 是合法結果。

## 與 Issue 文字的差異

Issue 寫「S85（復活動作與確認）」。實際上確認對話走 **S219**，S85 只是復活完成後的動作。因此：

- `WorldSession.cs` 加的兩個 case 是 **S219（觀察）與 S241**，不是 S85 與 S241。S85 已由 `ReceiveRecovery` 解析，再加一個 case 只會重複解析。
- S219 的 case 放在 `ReceivePartyHp` 同一個前置觀察 switch。必須在 Party／Duel 之前執行，否則 953、630 會先被吃掉，舊提示不會失效；`LoginReader` 也不能回捲，無法掛在既有鏈中間。
- `Recovery.cs` 的唯一掛載點是 `InitRecovery` 內的 `InitResurrection()`。世界狀態不需要掛鉤：S85 清除 `OwnDead` 後，提示會自行結束。

## 復活確認的行為

- 只有 `Ready` 且 `OwnDead`、尚未要求重新開始時才開啟提示；其餘情況忽略。
- 接受不會在本地復活。恢復仍走既有流程：S85 之後等 HP 與 S119。
- 提示在下列情況失效，舊畫面的回答不會送出：任何其他 S219、新的 321／322（取代舊訊息）、S85、世界重建、Reset、已要求 C177、連線中斷。
- 觀察不消耗封包：321／322 仍走 Trade 既有的非 252 路徑，舊交易、求婚、入盟邀請照舊失效。代價是 `unhandled[219]` 仍會加一，血盟的失效判斷依賴這個計數，所以保留。
- 回答後「死亡後重新開始」仍可使用，避免原服不回包時角色卡死。
- 321 與 322 的回復量差異由原服決定，客戶端不顯示也不推算。

## 移動鎖定的行為

S241 沒有解除形式，解除條件是引擎自己的政策，**不是原服規定**：

| 解除條件 | 依據 |
|---|---|
| 新的權威位置（自身 S87） | `C246` 非 127 分支是 S202/7 加傳送，最後一定有 S87 |
| 世界重建、Reset | 舊世界的鎖不跨世界 |
| ~~5 秒安全上限~~ | R5-D（T309／#736，gap-matrix 14.6）已拿掉：那是引擎自訂、原版沒有的上限。鎖定期間仍可用道具（例如傳送卷軸，`ItemAvailable` 不看移動鎖）或重新開始，兩者之後都會收到 S87 |

單獨的 S202/7 不解除：它也是物品拒絕的共用回包，不代表位置已校正。未定義的 S241 內容（非 0）記為未處理，不上鎖。

查詢點在 `MovementAvailable`，所以鎖定期間不送 C29，也不送 C225。送出閘門會再查一次，並遞增 `AppearanceRevision`，鎖定前排隊的請求即使在解除後才輪到也不會送出。**附帶影響**：攻擊、施法、門與傳送點都以 `MovementAvailable` 為前提，鎖定期間一併停止，直到收到 S87。另外，表情的 1234 ms 保留（`EmoteHeld`，R5-D）也併進 `MoveLocked`；只有 S241 本身看 `ServerMoveLocked`。

## 待驗證

- **原客戶端收到 S241 後是否自動回 `C246`。** 原服流程看起來需要它：`Locerr2Timer` 倒數結束只送 S241，修正位置要靠 `C246` 非 127 分支。本客戶端不送 C246，所以「修正人物錯位」選單目前只會鎖定到下一個 S87（例如傳送或重新開始），不會修正位置。C246 的 type 值沒有證據，本任務不猜測。
