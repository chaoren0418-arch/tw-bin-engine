## 欄位格式

`C/H/D` 為 1／2／4 bytes，小端序；`S` 為目前連線使用的 Big5（CP950）零結尾文字。`W` 為 UTF-16LE 文字，以 `00 00` 結尾（相對文字起點按兩個 bytes 對齊）。下表包含 opcode。

| 方向／子型別 | 格式與意義 |
|---|---|
| C87 `00/01/02` | `C87 C(type)`，要求一般／血盟／保管箱清單 |
| C87 `10/11/12` | `C87 C(type) D(id)`，讀信 |
| C87 `20/21` | `C87 C(type) H(0) S(收件人或自己的血盟名) W(標題) W(本文)`，一般／血盟寄信；H 由處理器讀取但不使用 |
| C87 `30/31/32` | `C87 C(type) D(id)`，刪除對應信匣的信件 |
| C87 `40` | `C87 C40 D(id)`，存入保管箱 |
| S186 `00/01/02` | `C186 C(type) H(count)` 後接 count 筆 `D(id) C(read) C(yy) C(mm) C(dd) S(sender) W(subject)` |
| S186 `10/11/12` | `C186 C(type) D(id) W(body) C(0)`；本文已含雙零結尾，`writeByte` 再補單零 |
| S186 `20/21` | `C186 C(type)`；無法寄送通知，**不是成功 ACK** |
| S186 `30/31/32/40` | `C186 C(type) D(id) C(1)`，刪除／保管確認 |

S186 清單標題的兩個零，分別來自 `writeByte` 及 `S_Mail` 的額外 `writeC(0)`；不可把 `writeByte` 當成只寫 raw bytes。所有 S 包再補零到 8-byte 邊界。清單日期不合法時可能為零；保留原始三個 byte，不推算世紀。

寄信刻意不套用通用 `LoginPackets.Pad`。伺服器 `readByte()` 取得從收件人結尾到封包末端的全部 bytes，要求偶數長度；若 Big5 名稱 byte 數為偶數，通用補零反而使該區段變成奇數。現有串流加密與 frame 包裝支援非 8 倍數長度，離線測試涵蓋兩種名稱奇偶與加解密往返。

## 文字、費用與限制

- 已查處理器／分割程式僅要求至少 4 bytes、偶數長度及兩個 UTF-16 雙零分隔；沒有固定的標題／本文字數上限或其他字元白名單。空標題／本文可表示。客戶端拒絕內嵌 NUL、未成對 surrogate，以及 CP950 無法編碼的收件人，避免截斷或替換。
- 本文允許換行與合法 Unicode。UI 的剩餘量以 UTF-16 code units 表示；補充平面字元占兩個單位。
- **客戶端傳輸上限**為 `LoginFrames` 的 body 10238 bytes，並非宣稱伺服器有這個本文上限。寄信大小為 `9 + 收件人 CP950 bytes + 2 × (標題單位數 + 本文單位數)`；超出即拒絕，不截斷。
- 一般信郵資 50 金幣、容量 20；血盟郵資 1000 金幣、每成員容量 50。費用／收件人存在／自己的血盟資格以伺服器裁定，不預扣金幣或假造成功。
- 一般滿箱回 S186 `20`；不存在收件人與金幣不足可走既有 S_ServerMessage。UI 顯示最近伺服器訊息並保留送出後的草稿，沒有自動重送。

## 伺服器現況與待驗證項目

- `getMails(receiver)` 目前回傳收件人的全部信件，未依 type 過濾；清單沒有每筆信匣型別，不能從封包判定個別信件屬哪一箱。UI 保留三類要求，明示「伺服器清單可能包含所有信匣」，不假造分類。
- 空信箱可能完全不回包。送出列表要求不清除已有資料，不以逾時判定空信箱。
- 一般／血盟寄出成功沒有專用 ACK。UI 顯示「已送出寄信請求」，同一視窗的該草稿送出後鎖定；使用者可選擇清空並寫新信。
- 保管成功只回 ID 與結果；清單沒有分類欄位，因此保留該列並顯示伺服器確認保管。刪除須等成功回包才移除。
- 世界重設、地圖 epoch 或 session 改變會使本模組快取與視窗失效；關閉視窗會撤銷尚在傳送閘門等待的操作。這是客戶端防止舊操作送出的策略。
- UTF-16LE 的端到端原生呈現、實際費用與收件結果仍需 dot 在授權 P24Lab smoke 核對；本次僅驗證來源格式、產品編譯及合成封包，不宣稱真機完成。
