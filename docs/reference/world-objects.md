# 世界物件類功能的原版表現（T182／#484，G10c）

查證日期：2026-11-08（Asia/Taipei）。範圍：T103 拾取時序、T136 門、T143 幽靈、T144 座標分享格式、T151 復活確認（含死亡畫面）。

**方法（照 #417）**：唯讀、靜態分析未加殼的 `TW1608262200.bin`（SHA `e12949cf…641a2`，已核對）。IDB 用 P01 的 `ida/03-ascii-isolated/TW1608262200.idb`，複製到 `scratch/rea/ida/tw16.idb` 後才開（SHA `3a0bf206…7e82f`，已核對）；工具為 IDA 7.7＋Hex-Rays，另以 pefile／Capstone 核對反組譯。subst 磁碟用 `W:`，每輪執行前都確認未被占用（同時段 `Q:`、`R:` 由 task-460 使用）。UI XML 用 `rea-scripts/ui_xml_decrypt.py` 解到 `scratch/rea/uixml/`，未進 git。沒有啟動遊戲、伺服器或 DB。

**地址換算**：File Offset（FO）＝ .text VA−0x400C00、.rdata VA−0x401400、.data VA−0x401800；.data 無初值的部分標為 bss。

**分級**：「已驗證」＝ 反編譯＋反組譯都看到；「推測」＝ 依命名、結構或旁證；「待驗證」＝ 需要真機或更多分析。

## 1. 物件點擊的共通流程（拾取與門都走這裡）

**已驗證：**

- 點擊物件進入 `sub_F112F0`（FO `0xB106F0`）。**自身死亡旗標 `byte_13CE3FD`（bss）為 1 時直接返回，不處理任何物件點擊。**
- 物件類別取 vtable `+108`。`sub_A41D10`（FO `0x641110`）判斷「可互動」：類別 ∈ {4, 6, 7, 8, 9, 12, 13, 14, 15, 18}，或 vtable `+112` 為真（個人商店）。
- 距離判定 `sub_500E40`（FO `0x100240`）：`|自身x − 目標x| ≤ 2r 且 |自身y − 目標y| ≤ r`。客戶端內部 x 是兩倍座標（送出時用 `((x−0x8000)>>1)+0x8000` 換回），所以 r=1 等於**遊戲座標的 1 格（含斜角）**。反組譯確認 `this` 是自身座標 `[0x153CE60]+0x10`。
- 在 1 格內而且類別是 9（地面物品）才直接呼叫 `sub_5001C0`（FO `0xFF5C0`）。其他情況（物件不是 9，或不在 1 格內）把 `dword_13CE400`（bss）設成 **3**。
- 模式 3 是「走過去再互動」：每步移動的 `sub_A3DE30`（FO `0x63D230`）在模式 3 下，檢查是否已到距離門檻（一般 1 格；類別 14 的 gfx 10445–10447 是 12 格；類別 6／12／15／18 依武器射程），到了就呼叫 `sub_5001C0`；路徑終點等於目標位置時也呼叫。

`sub_5001C0` 依類別分派：

| 類別 | 動作 |
|---|---|
| 9 | 拾取（第 2 節） |
| 7、8 | 送 `C_OPEN`（131）`chhd`：x、y、物件 id（第 3 節） |
| 14 | 送 opcode 121 `C_PLATE` `cd`（物件 id） |
| 4 | `sub_503BE0`（NPC 對話） |
| 6、12、13、15 | `sub_4F97A0`（送 opcode 51 `C_DIALOG` `cd`） |

**推測：** 類別 7、8 是門。依據：送出的 `chhd`＝x、y、id，與 3.81 `C_Door` 的 HHD 一致；名稱表 131＝`C_OPEN`。

## 2. T103 拾取時序

### 原版來源

**已驗證：滑鼠點擊拾取（`sub_5001C0` default 分支）。**

1. 先擋掉幾種情況：`byte_13CE51E`（bss，幽靈＝2，見第 4 節）不為 0 時不拾取；物件 `+85` 為真時不拾取（`sub_A42C30`）。物件與自己不同格時，`sub_F12490` 檢查朝物件方向的相鄰地格旗標 bit 0（推測是牆）；被擋就不拾取。
2. **送出前先在本機把角色轉向物品**（物品不在腳下時），用 vtable `+104` 或 `+84` 加 `sub_A40EC0` 算出的方向。
3. 數量：堆疊 ≤1，或「全部拾取」選項 `byte_135C1E4`（FO `0xF5A9E4`）開著時，**直接送整疊**。否則開數量輸入提示 `sub_4FD2F0`（FO `0xFC6F0`）：字串表 121 加數量，回呼 `sub_500A00`（FO `0xFFE00`）。空白輸入等於整疊；輸入 0 或大於持有量就不送。
4. 節流：`now ≥ 上次 + 986 ms`；旗標 `dword_13CE514 & 0x10000` 時改為 600 ms。時間戳 `dword_139FBA8`（FO `0xF9E3A8`）由三條拾取路徑共用（`5001C0`、`500640`、`500A00`）。節流未過時**不送、也不排隊**。
5. 送 `C_GET`（23）`chhddc`：x、y、物件 id、數量，最後一個 byte 是 `sub_9E4680(id)`（id 是否在某清單內，語義未明）。送出後設 `dword_13D4408 = 23`。

**已驗證：鍵盤拾取（動作 `Action_Loot`，字串 VA `0x119FA88`／FO `0xD9E688`）→ `sub_ADA840`（FO `0x6D9C40`）→ `sub_500640`（FO `0xFFA40`）。**

- 幽靈、死亡或狀態 24 時不動作。
- 依序掃描可見物件，取**第一個**在 1 格內、類別 9、數量非 0、沒被牆擋的物品。
- 同樣先轉向、套用同一個節流，**一律整疊拾取，不問數量**。
- `Action_Loot` 是 `Actions.xml` 的 action 類動作（icon 5363），放在動作列使用，預設按鍵沒找到。

**已驗證：「全部拾取」切換。** `Action_LootAll`（VA `0x119F6F0`）→ `sub_ADA880`。HyperText 動作 `HyperActGetAll`（vtable `0x11A94A0`）→ `sub_582E30`（FO `0x182230`）。兩者都會切換 `byte_135C1E4`，並刷新選項頁 `option13`。

**推測：** `0x10000` 是加速類旗標。依據：與 REA B07 的「加速 600 ms」說法相符，但實際來源沒有追。

**待驗證：**

- 收到 `S_ACTION` 15 後的本機拾取動畫時序。`sub_92CB70` 對一般動作只轉交 vtable `+100`／`+76`，沒有拾取專屬分支。
- `sub_9E4680` 清單的語義。

### 引擎現況

`Ground.cs`、`GroundUi.cs`、`PickupPresentation.cs`：

- 由地面清單選物品，按鈕或 P 鍵送 C112，數量取文字框，預設 1。
- 本機距離門檻是 **3 格**，超過就提示「請自行靠近」，不會自動走過去。
- 節流 900 ms，並等 S158/15 回報，最長 3 秒。
- 轉向等收到 S158/15 後才用 `PickupHeading` 計算。
- 鍵盤 P 拾取的是「已選取的物品」與文字框數量。

## 3. T136 門

### 原版來源

**已驗證：**

- 點門走第 1 節流程。不在 1 格內就進入模式 3，**先走到 1 格內，才由 `sub_5001C0` 送 `C_OPEN`（131）`chhd`**：x（換回遊戲座標）、y、物件 id。送出位置 `0x500377`。客戶端不區分開或關，只送這一個請求。
- 門的通行屬性：`S_CHANGE_ATTR`（38）`hhcc`。`sub_932470` 把座標換成內部座標（`c + 2x − 0x8000`、y）後，呼叫 `sub_F07190` 更新地圖屬性。欄位與 3.81 S209（x、y、方向、可否通行）形狀一致。
- 門的開關動作：`S_ACTION`（226）`dc` 由 `sub_92CB70` 交給物件 vtable `+100`（`sub_A3EBF0` 為真時）或 `+76`。沒有門專屬分支。

**推測：** 門是類別 7／8（依據見第 1 節）。

**待驗證：**

- 類別 7 與 8 的差異。
- 門類別 vtable 如何處理動作 28／29。沒有追到門類別的 RTTI。
- `hhcc` 兩個 c 在 `sub_932470` 中各自的用途。Hex-Rays 只顯示一個參與座標計算。

### 引擎現況

`Doors.cs`：

- 依完整 DoorPack 特徵辨識門。可見的門都能點，**沒有距離限制，也不自動走近**。
- 送 C41 HHD。
- S158 28／29 切換門的動作；S209 更新阻擋格。

## 4. T143 幽靈模式

### 原版來源

**已驗證：**

- `S_PUT_OBJECT` 的 flags byte：bit 0x80 → 描述子 `+100`（`sub_948A60` → `sub_9262D0`，FO `0x5256D0`）。其他位元：0x01→`+104`、0x02→`+103`、0x04→`+102`、0x08→`+101`、0x70>>4→另一欄。
- 自身物件：`sub_A51920`（FO `0x650D20`）呼叫 `sub_A50100(+100)`（FO `0x64F500`）。幽靈時 **`byte_13CE51E = 2`**。不是幽靈時，依 `sub_5069E0(1)` 與等級 ≤ 50 設 1 或 0（狀態 1 的語義未明）。
- 其他物件：`sub_A45480` 把旗標存到物件 `+88`。
- `byte_13CE51E != 0`（含幽靈）時，本機直接擋下的功能（各函式開頭就返回）：
  - 拾取：點擊 `sub_5001C0`、鍵盤 `sub_500640`／`sub_ADA840`。
  - F 鍵瞬移檔 `teleport_F%d.txt`：`sub_8BA150`。
  - 道具／技能快捷：`sub_98F330`、`sub_9A6FB0`、`sub_9A78A0`、`sub_9AB960`、`sub_A5B9C0`、`sub_E99750`。
  - 自動攻擊／移動相關計時：`sub_A3D520`、`sub_9F32A0`、`sub_EDFD70`、`sub_EDFE70`、`sub_88F070`。
  - 這些函式同時也檢查死亡旗標。
- 幽靈時**仍可點**門（7／8）、NPC（4）、類別 14。`sub_5001C0` 只在 `byte_13CE51E == 1` 時限制成 4／14，等於 2 時放行。
- 幽靈中，自身外觀變更（`sub_A43B50`，FO `0x642F50`；被 `S_RESURRECT`、變身等呼叫）**對自己無效**，直接略過。
- 離開：`HyperActExitGhost`（vtable `0x11A93E0`／FO `0xDA7FE0`）→ `sub_582C20`（FO `0x182020`）。只在 `byte_13CE51E == 2` 時送 **`C_EXIT_GHOST`（179），無欄位**。這個動作在 HyperAct 工廠 `sub_BB5180`（FO `0x7B4580`）以名稱 **`exitghost`** 註冊。同一張表還有 `npcNameView`、`doreceive`、`banish` 等 HyperText 動作名稱。

**推測：** 原版用 HyperText（NPC 對話 HTML）的連結動作 `exitghost` 離開幽靈，沒有常駐 HUD 按鈕。客戶端 HTML 在加密的 `Text.pak`，未解開，沒找到哪一頁有這個連結。

**待驗證：** 其他物件 `+88` 的繪製效果（是否半透明）、自身幽靈的畫面效果。都沒有追到讀取者。

### 引擎現況

`GhostMode.cs`：

- 以自身 S87 `flags & 0x80` 判定幽靈。HUD 常駐「離開幽靈」按鈕，送 C173 無欄位，15 秒防重送。
- 不改外觀。
- **不在本機擋拾取、快捷或瞬移**，交給伺服器判定（`docs/protocol/ghost-mode.md`）。

## 5. T144 座標分享格式

### 原版來源

**已驗證：送出。**

- 入口：地圖視窗事件表 `sub_8DE770`（FO `0x4DDB70`）註冊的 **`TransferMenu`**（字串 VA `0x1180BD8`／FO `0xD7F7D8`）。同一張表還有 `MapName`、`QuestToggle`、`ShowBookmark`、`SaveMenu`。
- 點擊（0x201）→ `sub_8E0620`（FO `0x4DFA20`）在聊天輸入列開提示（字串表 **1785**），回呼 `sub_8DC850`。輸入角色名、按 Enter 後，由 `sub_8D4A90`（FO `0x4D3E90`）送出。
- 格式依反組譯的壓棧順序：**`C_CHANNEL`（55）`ccshdd`＝ C55、C11、S（收件者）、H（地圖）、D（x | y<<16）、D（區域 id）**。與 3.81 C254/11 的 `S H H H D` 逐 byte 相同。
- 在 decrypted UI XML 中沒找到哪個按鈕綁 `TransferMenu`。

**已驗證：接收。**

- `S_EVENT`（108）子類 0x6F，`shdd`（VA `0x93CBEE`）＝ S（寄件者，最多 13 bytes）、H（地圖）、D（x | y<<16）、D（區域 id）。
- 交給 `sub_8D43B0`（FO `0x4D37B0`），依下表處理：

| 條件 | 處理 |
|---|---|
| 功能物件 `+16` 為 0 | 只顯示系統訊息 **2139**，不記錄 |
| 一般 | 記錄（地圖、x、y、寄件者）到清單，**最多 10 筆**，滿了先刪最舊的 |
| 區域 id ≥ 100 | 在村莊地圖表 `+168` 找名稱 |
| 區域 id < 100 | 在世界地圖表 `+164` 找名稱 |

最後用 `sub_7DC850` 在聊天顯示字串表 **1784**，格式化參數是寄件者與區域名稱。

**推測：** 區域 id 就是 `MapSystem.xml` 的 Map id。依據有兩點：該 XML 註明「World Map ID Range 0 ~ 99」與「Village Map ID Range 100 ~ 999」，剛好與上面以 100 分界的兩張表一致；每筆有 `mapDesc`（名稱字串 id）。所以聊天訊息顯示的是**寄件者＋地區名稱**，不是數字座標。送出時的區域 id 取自位置物件 `+0xC`，計算方式沒有追。

**待驗證：**

- 字串 1784／1785／2139 的實際文字。字串表在 `Text.pak`，已加密。
- 10 筆清單在哪個 UI 顯示、能否點擊。
- 伺服器回包 S71 1782／1783 走一般 `S_MESSAGE_CODE`（102，`sub_942B40`）的字串表，本輪沒有逐條看。

### 引擎現況

`LocationShare.cs`、`docs/protocol/location-share.md`：

- 聊天輸入 `/loc 角色名` 送 C254/11，**區域 id 固定送 0**。
- 收到後在密語頻道加一行「`地圖 {map} ({x}, {y})`」，加底線可點。點了在場景放 ⊕ 標記；跨圖或在視野外時，在畫面上方提示。
- 歷史與聊天共用最多 100 筆。S71 1782／1783 用引擎自寫中文。
